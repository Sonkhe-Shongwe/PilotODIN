## Why the proposed ObTrace-only path cannot close the current gate

Microsoft [ObHandleEvent](https://learn.microsoft.com/en-us/windows/win32/etw/obhandleevent) exposes a handle number, object pointer, name and type. [FileIo_ReadWrite](https://learn.microsoft.com/en-us/windows/win32/etw/fileio-readwrite) exposes the opened object instance, IRP, thread and FileKey, not the numeric handle used to issue the write. [GetFinalPathNameByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlea) requires a usable file handle; a foreign process's numeric handle is not one. [Socket Handles](https://learn.microsoft.com/en-us/windows/win32/winsock/socket-handles-2) warns against DuplicateHandle on sockets. The G2.18 prohibition on arbitrary foreign duplication remains binding.

Current code independently requires the authentic original file handle and a final path/volume witness (n12_physical_destination.py), then exact request-time path and original-handle/FileObject/IRP association (n12_fileio_pair_contract.py). n12_obtrace_feasibility.py accepts only caller-supplied known self-file path witnesses and refuses ambiguous handle epochs. A generated successful test could validate the self-file join but cannot supply the missing actual WebView witness or distinguish indistinguishable multiple-handle writes. Full integration of that test cannot cure this logical gap. This is a no-go for the *currently demonstrated* architecture, not a claim that all Windows instrumentation is impossible.

Sysmon [Event 5](https://learn.microsoft.com/en-us/sysinternals/downloads/sysmon) provides event UtcTime, GUID and PID; [GetProcessTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes) supplies actual handle creation/exit FILETIME. No documented exact cross-provider equality. Existing shadow_handle_exit_review is candidate-only. No approval to change strict time predicate.
