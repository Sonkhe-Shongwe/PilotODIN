## 3. Remediation work packages and completion criteria

**R1. Canonical data correctness and import resource safety (CF-02 first, then CF-01).** Consolidate data readers and identifier typing. Exercise generated leading-zero OrderNumber/SKU values across import, Quality and ML. Preflight XLSX expansion and CSV limits before full parsing. Preserve originals and late-encoding fallback. **Exit:** same source produces the same schema everywhere; oversized inputs fail within measured resource budgets without modifying a project.

**R2. SQLite and Quality consistency/performance (CF-03, CF-04, CF-07, CF-13).** Audit existing DB foreign-key consistency before enforcement. Shorten write transactions by moving expensive validation outside them while committing under strict version/archival rechecks. Add safely keyed materialization caching and explicit connection closure. **Exit:** correct immutable history, receipt/undo behavior, no stale commit, deterministic resource lifecycle and measured reduction in redundant reads.

**R3. ML and AI workload safety (CF-05, CF-08).** Enforce bounded ML/inference concurrency on ordinary 8 GB hardware. Move model hashing off synchronous UI handling and avoid lengthy mutex ownership. Maintain truthful cooperative cancellation. **Exit:** no duplicate workers, controlled simultaneous requests, honest error states and representative RAM/headroom evidence.

**R4. Product trust boundaries and desktop storage (CF-06, CF-09, CF-10, CF-11, CF-14).** Strengthen dev authorization, migrated artifact trust and reproducible dependency provenance; make browser profile ownership explicit where supported. **Exit:** source-reviewed threat boundaries and scoped runtime behavior established when necessary under separate native consent.

**R5. Targeted maintainability (CF-12).** Refactor touched interfaces and cut duplicated state or reader logic only as needed for proven fixes. **Exit:** reduced coupling, same externally observable product behavior, minimal focused regressions.

For every package: (1) find and explain the root cause; (2) produce the smallest useful code correction; (3) use one direct regression or relevant resource measurement; (4) check existing affected product flows; (5) record exact GitHub source and actual CI outcome. If a check fails, return to the code/call path before expanding testing infrastructure. **Never award native or phase acceptance for synthetic success.**
