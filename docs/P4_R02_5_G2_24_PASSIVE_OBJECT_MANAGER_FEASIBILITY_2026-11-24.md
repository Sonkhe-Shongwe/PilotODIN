## Independent API evidence

Microsoft documents [ObTrace](https://learn.microsoft.com/en-us/windows/win32/etw/obtrace), [ObHandleEvent](https://learn.microsoft.com/en-us/windows/win32/etw/obhandleevent) and [ObHandleDuplicateEvent](https://learn.microsoft.com/en-us/windows/win32/etw/obhandleduplicateevent). The documented handle create/close events carry handle and object values plus object type/name; the duplicate event additionally describes duplication. ObTrace documentation describes system-trace enablement using TraceSetInformation and PERF_OB_HANDLE, not simply adding its classic provider GUID to the existing logman manifest-provider list. Use documented APIs only. Exact modern hosted Windows schema, pointer width, header process ownership, time semantics and compatibility with the current Microsoft-Windows-Kernel-File session are not verified. [FileIo_ReadWrite](https://learn.microsoft.com/en-us/windows/win32/etw/fileio-readwrite) describes classic FileObject, FileKey and IRP identity; it does not expose the issuing numeric HANDLE. Do not assume the current manifest provider and classic MOF identifiers are interchangeable.

G2.18 remains governing: [DuplicateHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle) warns about socket reference counting; IFS sockets can be File objects. No foreign duplication, PROCESS_DUP_HANDLE escalation, undocumented global handle-pointer table, kernel driver or injection is authorised. Object-manager tracing is a passive candidate, not evidence that any particular object is a disk file or that a name is a physical destination.
