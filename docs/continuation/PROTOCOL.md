# Continuation v2 | Recovery and ownership contract

Adopted for repository continuity only, under owner request 26 November 2026. No product, acceptance, evidence-method, phase or restricted-operation authority changes. The original v1 protocol remains accessible at its existing path and immutable pre-migration snapshot; v2 supersedes its startup reading order and live-state ownership only. All substantive safeguards remain binding.

## Ownership

- AGENTS.md: permanent entry point, non-negotiable rules. CONTINUATION_STATE.json: sole live operational state, next action, pending operations/runs and current permission status. It contains a derived score projection, not acceptance authority.
- Specifications and owner decisions: normative product requirements and rationale. Phase policy and product directive control authority/sequence. The original Master Reconstruction Blueprint and explicit owner decisions outrank agent summaries. If a required blueprint detail is unavailable, stop that decision or obtain original, not a guess.
- Official scorecard: earned points. Evidence ledgers: immutable dated receipts, exact runs/results, failure history, independent artifact evidence. Documentation index: discovery. Do not copy receipts or live state into several documents. Old handoff/journal are compatibility routes; original versions accessible in Git.
- New decisions use existing decision index or owning spec; do not create another parallel authority register. State's restricted approval records link explicit owner authority and exact scope; recording them never grants authority. A consumed or uncertain approval cannot be reused. No credentials or raw owner data in state or logs.

## Startup (progressive disclosure)

Read AGENTS and state at actual branch HEAD. Use exact blob-bound line ranges when provided; if the blob changes, resolve the heading again. Validate state syntax, invariants, local references and score projection with optional standard-library validator; an agent with connector-only access can perform equivalent checks. Do not install anything or trigger CI to validate continuity. Validate live Git and exact-source CI separately: HEAD is observed externally, state.checkpoint.parent_sha is the checkpoint's expected parent, not a self-referential HEAD. Check operation commit/diff/run outcomes, pending jobs, approvals and any new authoritative owner decisions. If state is stale, malformed, Git unavailable, or permissions conflict, stop consequential execution and reconcile against last known good Git snapshot and governing evidence. Never infer clean owner-local state. Read task.read sections and relevant authority only; retrieve historical context when needed, including external blueprint when required.

## Operation lifecycle

Task states READY, PREPARED, IN_PROGRESS, PUBLISHED, VERIFYING, BLOCKED, CLOSED. Operation states NONE, PREPARED, ISSUED, UNKNOWN, RECONCILED. Before consequential execution persist stable operation ID, expected HEAD, scope, intended paths/target, explicit authority, expected evidence and recovery instruction in state; include exact approval/one-use marker and run attempt when relevant. Record actual execution/unknown outcomes, not assumptions. A PREPARED record is intent only. For unknown push/dispatch or concurrent branch change, inspect branch/history/diff and exact runs before retry; potentially consumed restricted authority remains unavailable until reconciled. Disarm exact owned one-use activation only when safe with expected HEAD; never activate again to discover whether it ran. Record failure before corrective action. Pending is not pass; source verification is not native/physical/release acceptance. Closing views or chats does not cancel or imply completion of operations.

## Checkpoint transaction

Use one non-force expected-HEAD publication for a coherent result, after inspecting matching workflows and job scope. Write ahead separately only for consequential operations, not every read/small edit. Update state in place, append a single dated receipt if material, update decision/spec only on actual contract decision, scorecard only when earned. Reference immutable parent SHA and operation ID; resolve actual commit after publish. Reconcile pending/unknown work rather than replay. Preserve historical evidence, original data, local unknown work and existing approvals; no acceptance changes from docs cleanup. Do not append chronology to state. Keep next task and 2–3 dependency-ordered checkpoints. For a blocked task, name the owner decision or evidence needed and do independent authorised work only if useful. No state change means no commit. Report scope, exact verification, progress delta, blockers and next action.

## Recovery, verification and rollback

The [original 12 recovery scenarios](../CONTINUATION_RECOVERY_CHECKS.md) remain the reference. The current validator parses the P4 official scorecard; any future authorised phase transition must adapt that projection and validation without granting authority. Validator is advisory/read-only: it checks structure and projections, not permission authenticity, live network, binary provenance, product behavior, or actual CI. Never grant or award automatically. At meaningful checkpoints verify path references, selected anchors, actual source SHA, pending/consumed status, exact source vs official progress, and matched workflow safety. Audit periodically or when inconsistency is found, not at every clean chat transition. Preserve previous state via Git parent and recover with a non-force forward correction; no history rewrite. If v2 itself is incomplete, consult the pinned pre-migration handoff/journal/protocol and recover migration commit first. If repository unavailable, report blocker and do not replay. Historical archives are not work orders.
