## 1. Current architecture and real evidence

Tauri/Rust starts native main WebView from config, React main.tsx starts analytics using desktopBootstrap, Rust supervises bundled Python engine with per-launch loopback token and lazy llama inference worker. SQLite metadata and original dataset/model files live under app_local_data_dir/data via PILOTODIN_HOME in packaged mode. Browser UI preferences live in WebView localStorage. Cloud off by default with Windows DPAPI and bounded consent paths. Reports and investigations are backend-owned persisted revisions/evidence; native report Save As uses a chosen local destination and verified staging. QA no-CDP runs a staged native debug app, an external Uvicorn backend and Vite, with its own disposable profile/ambient env, not the packaged production sidecar lifecycle.

## 4. Recommended target architecture, no framework rewrite

Rust owns desktop startup, application identity, workspace exclusivity, canonical configured roots and worker lifecycle. Backend receives only validated workspace paths and owns durable analytical state. WebView profile and disposable scratch are isolated from authoritative DB/datasets/artifacts; UI localStorage is preference state, never evidence authority. Backend's typed storage service owns originals, SQLite, artifact staging/commit/reconciliation, models, report evidence, and internal export scratch. Native user-approved export is an explicit exception outside app-owned roots, never a blanket write allowance. No blanket environment redirection, no replacing existing browser profile blindly, no removing user data, no broad OS filesystem permission change. Application-managed boundaries reduce accidental writes but are not independent prevention against all Windows runtime operations. Independent native evidence and protection controls remain required.

WebView2 documented Tauri dataDirectory defaults to app-local data and WebviewWindowBuilder::data_directory can select path, but Microsoft environment/registry overrides can change requested UDF; browser processes are associated with UDF and BrowserProcessExited signals release. See [Tauri WindowConfig](https://docs.rs/tauri-utils/latest/tauri_utils/config/struct.WindowConfig.html), [WebView2 environment](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/webview2-idl), [process model](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-model), [process events](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-related-events). Verify exact locked SDK/API before implementation; no promise all Edge/Windows cache writes follow UDF.
