## 1. What is being evaluated (frozen before future observations)

- **Decision owner:** The repository's human owner/maintainer, who would decide whether a focused extra frontend check merits attention before pushing a genuine, separately justified code change. Owner approval of *evaluation* is recorded; an independently verified human pre-push choice, actual review time and business acceptance are **NOT SUPPLIED**.
- **Decision moment:** Before a relevant frontend change is first pushed; source paths, staged patch digest, base commit and known source/test/config content can be inspected then. Workflow outcome, logs, fixes and other post-push information must never be inserted into the predecision.
- **Existing control/baseline:** Carry on with all standard CI checks as they already run naturally. The shadow study cannot dispatch CI, run an additional test, alter triggers, suppress safety checks, change a development decision, or ask for artificial code pushes.
- **One fixed outcome workflow:** Existing [P1 Isolated Frontend Verification](../.github/workflows/p1-isolated-frontend.yml), on the current development branch. P4-56 found 214 historical runs with 214 distinct SHAs, but 57 cancelled and only 31 completed failures; that snapshot is historic feasibility evidence, not a future event rate or predictive model. Do **not** reopen P1 development.
- **Eligibility:** Consecutive, independently justified **future** change proposals that would normally match the selected P1 workflow's existing `push.paths` filters. No selective inclusion after seeing outcomes. Documentation-only, backend-only and this charter's commits are ineligible. If workflow filters, branch, or decision rule change, **pause** and separately amend/re-freeze the protocol before using new records.
- **Primary observable outcome:** The earliest naturally triggered P1 workflow run for the eligible pushed change, attributed to its actual new `head_sha` and verified run ID. Record `success`, `failure`, `cancelled`, `skipped`, `queued`, or `unknown` exactly. Cancellation/queue/absence of a run is not a failure, a pass or a missing-value zero. Later reruns must not replace an inconvenient first result.

### Frozen manual shadow recommendation rule (not a trained predictor)

For an eligible proposed change, set `extra_preflight_recommended=true` **only** if its proposed changed paths include TypeScript/TSX under `frontend/src/`, or any of `frontend/tsconfig.json`, `frontend/vite.config.ts`, `frontend/package.json`, `frontend/package-lock.json`. For this case record `proposed_check="npm run build --prefix frontend"`. This is a *hypothetical additional pre-push compilation check*, **NOT permission to execute it**.

For other eligible changes (for example test-only, E2E-only, frontend static assets or the selected workflow file), record `extra_preflight_recommended=false` and `proposed_check=null`. Record a brief specific pre-push rationale and exact changed paths. This simple fixed rule may miss test-only failures, include false positives, and have low variance; those are limitations to measure, not reasons to edit it after results.

**No machine-learning fit, threshold tuning, automatic model advice, preflight-run dispatch or actual workflow change is authorised.** No source or unit-test implementation is needed to activate this shadow-only manual protocol.

## 2. Manual, prospective workflow

1. **Before a genuine eligible push:** Human owner or an explicitly instructed human-supervised operator records a fresh `change_id`, UTC decision time, existing branch/base SHA, actual staged patch SHA-256, planned changed paths, frozen yes/no recommendation, proposed check and rationale in a **private** `pre.jsonl` file conforming exactly to [P4-57's existing schema](./P4_57_LOCAL_SHADOW_DECISION_LOG_VALIDATION_2026-11-12.md). The patch digest must cover the proposed patch bytes using a documented reproducible method; reconcile it with the future commit. If no independently timed genuine pre-push record exists, **exclude the change from prospective evidence**; do not backfill it.
2. **Independent prior-time witness:** Where privacy allows, post only the sanitised change ID, branch, base SHA, patch digest, changed paths and frozen shadow recommendation to [owner evidence Issue #9](https://github.com/Sonkhe-Shongwe/PilotODIN/issues/9) **before** the actual push. Retain GitHub server `created_at`/any edit metadata as external timestamp evidence and reconcile with the real commit. If this safe witness cannot be provided, mark temporal provenance **NOT INDEPENDENTLY VERIFIED**, not verified by local self-reported timestamps. Never publish a raw patch, private employee minutes, credentials or confidential paths.
3. **After the ordinary workflow has naturally run, with NO new CI dispatch:** Independently read the existing GitHub commit and run records at the correct SHA. Append a local private `post.jsonl` record using the exact [P4-57/P4-58 validation schema](./P4_58_SHADOW_STUDY_ATTRIBUTION_IDENTITY_CORRECTION_2026-11-12.md). Link a specific verified run ID once globally; record the real push and run-start times, conclusion, independently reviewed failure attribution or `unattributed`, supporting URL when verified, and real human repair/preflight minutes only if actually observed.
4. **Schema check only, locally/offline on private records (optional):** `python qa/p4_shadow/validate_shadow_log.py <private-pre.jsonl> <private-post.jsonl>`. This existing validator does not access GitHub, capture events or write evidence. Structural PASS never attests the independent clock, run authenticity, patch equivalence or business utility.
5. **Do not publish private observation logs or automate monitoring.** Owner may request a later explicit evidence reconciliation from sanitised, independently verifiable GitHub references. The current approval does not authorize this assistant to continue watching or collecting data between sessions.

- Report **eligible proposals**, true predecision coverage, records with independently attested pre-push timestamps, post-run matching rate, cancelled/skipped/queued/no-run count, legitimate success/failure counts and proportion of failures classified `new_actionable` by independently reviewed logs. - Report the fixed rule's true/false positives and misses **only** against independently adjudicated, actionable failure labels; never treat all CI red runs as defects or retrospectively relabel decisions to improve results.

A measured human debugging interval is not interchangeable with CI wall-clock runner time. Missing human minutes remain `null`, not zero.
- Initial feasibility review may use 20–30 distinct genuine future eligible changes **if they naturally occur**, only to assess recording completeness and label reproducibility, **not** as sample-size certification, an accuracy claim or Gate C acceptance threshold. Do not create commits to satisfy a quota.
- Before any actual extra-preflight execution, controlled comparison, quantitative power analysis, training or phase closure, obtain **separate** owner authorisation and a credible operational benefit/cost and lawful-purpose assessment. Gate C's independently corroborated real decision owner, label origin, as-of feature availability, group/time independence, baseline and benefit requirements remain unchanged.
- **Stop/pause** if human prior-time evidence is absent, a rule is changed mid-stream, commits cannot be reliably linked to one workflow, data provenance is sensitive, or prospective logging interferes with normal development. Accept a no-suitable-objective conclusion if no valid operational case emerges.
