## 2. Layered architecture and trust boundary specification

These are responsibility layers within the existing stack, not seven services or a product rewrite.

| Layer | Owns / source seam | Input -> output | Cannot do |
| --- | --- | --- | --- |
| L1 Discovery | Existing release/graph reviewers and candidate inventory | Source intent, upstream metadata -> reviewed candidate graph and expected rows | Resolve silently or mark actual bytes verified |
| L2 Trust policy | Pinned plans, build_input_policy_v1, future reviewed versioned READY contract | Reviewed graph, toolchain identities, independent expected digests and dispositions -> exact profile expectation | Read observed receipt as self-authorising expectation |
| L3 Controlled acquisition | Disabled hosted adapter, one-use authorisation and bounded request/response receiver | Exact source, operation marker, rows and residual caps -> transient immutable bytes | Install, execute, extract, retry, widen request scope |
| L4 Format verification | v2 inspector; separate archive/PE/GGUF validators by format | Immutable byte snapshot + exact row + budget -> typed integrity/refusal receipt and bounded notices | Access network, write owner cache, invoke subprocess or grant permission |
| L5 Evidence and provenance | v2 codec, v3 settlement, bounded receipt bundle/ZIP replay and durable ledger | Verified result/notice bytes -> canonical digest-bound evidence, independent replay and provenance disposition | Reinterpret replay as original archive reinspection or legal approval |
| L6 Verified input repository | Future owned cache/generation contract, immutable lock/manifest and publication pointer | Separately acquired, verified bytes + complete profile -> immutable staged inputs | Repair missing input, overwrite previous generation, publish solely from its own observed receipt |
| L7 Build consumption | Existing guarded entrypoints and preflight, separately authorised consumer | Approved profile + exact staged bytes + independent execution authority -> future build receipt | Enable installer or build on the strength of a source-only result |

**Dependency direction:** L1 -> L2 -> L3 -> L4 -> L5; only a separately authorised byte-retaining acquisition/publication transaction can establish L6; L7 validates L2/L6 together and has no implicit network fallback. Evidence is a side-channel for independent review, not a bypass. The policy controls capabilities, not arbitrary environment switches. Keep historical pinned modules/receipts untouched. Use standard library and existing graph tools; no new service, package manager, automatic trust store or global refactor.

### Resource and durability design

Current inspector maxima include 36,607,512 archive bytes, 50,000 entries, 1 GiB declared per-wheel expansion and 4 GiB cumulative expansion, 16 MiB control and path ceilings, 32 MiB batch raw notices; evidence codec permits 64 MiB encoded batch. Residual previous proposal: 63 requests, 225397605 body bytes, 4294072708 expanded, 33549191 raw notice bytes, 67097955 evidence bytes; bundle 68457827, outer ZIP 69506403. These are ceilings, not simultaneous RAM measurements. Receiver uses disposable TemporaryFile then byte snapshot; member streaming does not eliminate captured controls, JSON/base64 copies, in-memory inventories and replay ZIP/bundle copies. Measure generated near-bound fixtures separately for peak RSS, scratch disk, elapsed and failure settlement; test limits without allocating full 4 GiB, use scaled-down adversarial budgets plus representative bounded inputs. No owner 8 GB claim or actual runtime test. Never raise caps for convenience; if limits/retention/transfer change, require new exact scope review.

Durability: previous five notice documents are in Git-pinned envelope 1adcd112c54ffa90ee638bcd7598d879e01798bc; only receipt evidence, not full wheel bytes. Current receipt-only artifact has seven-day retention in prior plan. Before activation choose explicit durable preservation of independently replayed new notices within existing authority or seek separately scoped permission; if Git publication is contemplated, review actual notice redistribution and size before storing, no arbitrary binary/receipt upload, do not assume new retrieval authorised. Keep small canonical settlement/digest records durable, and plan a later separate exact byte-retaining acquisition into disposable owned verified cache if required for build. Do not falsely label 68 receipt-verified archives an available offline wheelhouse. Retain old and failed generations; post-publication uncertainty means reconcile, never replay blindly. No new cache implementation in this review.
