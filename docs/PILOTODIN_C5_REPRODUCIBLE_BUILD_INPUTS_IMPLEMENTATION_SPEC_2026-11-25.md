## 2. Architecture decision and trust boundaries

Keep React/TypeScript/Vite/npm, Tauri/Rust/Cargo (including the authorised local shell 2.6.0 derivative), Python/FastAPI/PyInstaller and existing GGUF/llama.cpp architecture. Preserve the current locks, dependency ranges as reviewed intent inputs, model choice, existing PDF renderer and offlineInstaller intent. No Poetry/uv, new package manager, new build service, version upgrades, automatic resolver or native bundler patch in C5. Source test environment, browser-only development and production/freezer are distinct profiles. A source lock is not an offline asset cache, a cache is not provenance, and provenance is not license approval or runtime acceptance.

Selected approach:
1. A small repository-owned standard-library preflight validates a reviewed versioned manifest/lock and exact local input bytes. It never runs a resolver, downloads, launches executables, imports application/third-party code or mutates input trees. Missing/unknown evidence is a BLOCKED result. Keep production manifest explicitly incomplete until genuinely populated. Do not introduce executable user-provided commands, automatic fallback or a new trust store.
2. Existing entrypoints invoke a scope-specific guard before dependency setup, venv/directory creation or package/build subprocesses. Production installer entrypoint is unconditionally frozen as first executable action (exit 2); existing npm/Tauri deny hooks and disabled workflows remain. No environment variable can override that freeze. Sidecar/staging acquisition/build paths require independent scope authorization and verified inputs, not an installer bypass. Keep ordinary isolated source CI allowed; no product staging there.
3. Separate immutable reviewed expected inputs from mutable observed staging reports. An expected input must cite independent upstream metadata, trusted artifact receipt or pinned source and a review decision; never bless a locally generated hash simply by rewriting a manifest beside it. Production acceptance requires exact bytes and complete provenance. Use a source-controlled manifest digest/commit identity and an external disposable approved cache, never owner data.
4. A future approved build records toolchain identity, lock hashes, effective flags, platform, resolved dependencies, actual bytes and resulting output checksums. This provides repeatable verified inputs, not bit-for-bit determinism. No actual builds in C5.

Alternatives rejected: top-level pip freeze from arbitrary venv (incomplete, wrong platform, no hashes); one cross-platform hash list for all environments (marker/ABI ambiguity); forced all-version upgrades (breaks verified behavior); self-generated runtime manifest as sole trust root (can bless tampering); permanent online fallback/cache healing (violates fail-closed); switching to fixed WebView2 just for convenience (changes runtime/update behavior); patching CLI/bundler without reviewed authority. Reopen only for documented incompatibility, an owner-approved dependency/product change, or evidence that a required offline input cannot be supplied.
