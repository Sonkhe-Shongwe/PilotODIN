## Grounded problem

The latest owner-approved real no-CDP native [run #44893498723](https://github.com/Sonkhe-Shongwe/PilotODIN/actions/runs/44893498723) was **STRICT BLOCKED**: all nine scoped process lifetimes had a Sysmon Event 5 `UtcTime` earlier than ETW provider `ExitTime`, so the exact cross-source comparison failed, although all seven WebView children had recorded Sysmon termination events, full ETW start image/sequence, and the original app/launcher Windows handles agreed exactly with ETW birth and exit payloads. Precise observed differences: **launcher +3.2932 ms, app +7.7625 ms**, and seven child exit mismatches (per-child deltas withheld). The only failed check in the eight-source-condition diagnostic was `etw-exit-exactly-matches-sysmon`; all other named source conditions matched. This is not proof that a timestamp difference is harmless. [Complete original evidence](./P4_N12_STAGE1_NATIVE_SYSMON_ETW_EXIT_CLOCK_DIAGNOSIS_44893498723.md).

The repository's Sysmon parser consumes Event ID 5 **EventData `UtcTime`**, not EventLog `SystemTime`. [Microsoft Sysmon docs](https://learn.microsoft.com/en-us/sysinternals/downloads/sysmon) document process termination with a GUID, PID and UTC event timestamp; [Microsoft GetProcessTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes) documents Windows handle creation and exit FILETIMEs; [Microsoft's ETW process schema](https://github.com/microsoft/Tx/blob/master/Generated/Microsoft_Windows_Kernel_Process.cs) exposes a kernel-process ExitTime. **None is a published guarantee of tick-for-tick cross-source equality**, and the two values are not interchangeable just because both are UTC.

## How to close the physical evidence gap without guesswork

The existing [`qa/p4_research/n12_driver_handles.py`](../qa/p4_research/n12_driver_handles.py) already demonstrates a **Windows-only** original-handle collector: Win32 process snapshots, `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)`, `QueryFullProcessImageNameW` DOS/native forms, retained handles, and `GetProcessTimes` after exit. It polls every **0.01 seconds**, with `HANDLE_LIMIT=96`. This is a reusable engineering pattern, **not** proof all WebView2 children can be observed. Short-lived descendants may be missed, snapshot/read permissions may fail and PID reuse must never be resolved solely by PID.

**Proposed next source-only engineering checkpoint:**
- Design a *narrow* watcher rooted strictly at the isolated QA app parent, with separate no-CDP consent guard, prior-to-ready start and exact original-handle retention for every observed child. Do not scan owner data or allow unrelated processes to be credited.
- Join each retained witness by exact handle creation+exit FILETIME, full DOS/native image, Sysmon GUID/PID/birth and ETW PID/sequence, plus the independently verified parent ancestry.
- Compare expected **every** WebView2 and network descendant GUID to a unique handle witness; fail closed on missing, ambiguous, truncated/unsupported identity, duplicate, missed samples and incomplete capture. A partial inventory can only produce diagnostics, never complete-profile acceptance.
- Prove synthetic negative cases including PID reuse, early child exit, absent handle, handle-limit exhaustion, parent mismatch, wrong image, ETW loss, overlapping ETW lifetimes and unexpected profile processes. Keep independent original protected snapshots and strict default N12 intact.
- Review the specific collector source and source-only CI before requesting **fresh one-use approval** for a hosted native Stage 1 run. No native approval exists now; the lifetime workflow is `if: false`, and the consumed marker is absent.

This source-only review **does not** justify introducing an empirical 8 ms/10 ms threshold or removing the Sysmon exit witness. The shadow candidate requires a new independent full-lifetime child source rather than inferring the child's process identity from the short ETW stop name.
