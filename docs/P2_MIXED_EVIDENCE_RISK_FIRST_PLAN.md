## 5. Predict failure within failure

- **False fixture success:** arithmetic oracle must be independently verified before app interaction; fixture mismatch BLOCKs test, never normalizes actual product output to expected.
- **Stored model vs real training:** seeding an evaluated result is allowed for reporting **only**; do not claim ML end-to-end acceptance.
- **PDF metadata nondeterminism:** compare semantic extracted texts/provenance against one frozen revision; only SHA-match *the same exported response bytes* when transport is in scope.
- **Text is not visual proof:** verify chart spec/caption and basic drawing geometry separately from PDF text; flag missing geometric evidence as NOT_TESTED.
- **Silent bounds:** fact cap 24, rows 40, findings 30 and graph caps may be deliberate, but omission should be disclosed to reader. Do not label a product defect before a concrete failing fixture.
- **Half-created project/report:** if precondition missing, stop chain; record BLOCK, clean only test-owned processes; never touch normal `PILOTODIN_HOME`.
- **Old-run contamination:** no arbitrary older DevQA export paths for this fixture. Use new `runs/P2-MIXED-REPORT-<id>`; verify run manifest/source ID association.
- **Diagnostic collection error:** always print explicit failure stage and local test log path if ZIP cannot be written; no false final PASS.
- **Privacy in diagnostics:** use sentinel-presence booleans, not copied row/holdout text or raw rendered files.
- **Change propagation:** if only Python rendering changes, rerun affected reports/unit/semantic gate; frontend TS/Vite only if frontend changed; native Tauri only if native/file export contract materially changed.
